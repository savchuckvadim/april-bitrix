Бэкенд: kpi-report-sales (отдельный репо). Фронт: `apps/kpi-sales`.

## 1. Симптом

Запрос эфирного времени за период > ~5 месяцев падает: UI показывает
«network error» (это `net::ERR_EMPTY_RESPONSE`/обрыв — см. родительский док).
Причина: ручка синхронная — пагинация `voximplant.statistic.get` (~2 стр/сек
под рейт-лимитером) крутится прямо в HTTP-запросе; большой период × отдел =
сотни страниц = десятки минут при открытом соединении. Страховка
`maxRows → truncated: true` уже есть, но это костыль: отчёт неполный.

Кэш повторных запросов уже работает хорошо (те же даты — мгновенно) —
его НЕ ломаем, а достраиваем.

## 2. Целевая архитектура (предложение)

### Ключевая идея: месяц — атомарная единица работы И кэша

Никогда не гонять «весь период» одним прогоном. Произвольный период =
Σ готовых месячных партиций + живой хвост текущего месяца.

### Умная оптимизация №1: партиция БЕЗ привязки к составу сотрудников

Сейчас ключ запроса включает список юзеров → смена фильтра сотрудников
убивает кэш. Предлагаю партицию `airtime:<v>:<domain>:<YYYY-MM>` —
воркер тянет статистику за месяц по ВСЕМУ порталу и складывает
**предагрегат** по `(userId, направление)`: суммарные секунды + счётчики +
rowsFetched/truncated. Тогда:

- любой состав отдела, view-as, карточка юзера — сборка из ОДНИХ И ТЕХ ЖЕ
  партиций, без новых походов в Bitrix;
- партиция крошечная (десятки строк агрегата, не тысячи raw-звонков);
- cron-прогрев тривиален: один job на месяц на портал.

Проверить перед стартом: текущий `AirtimeStatisticResponseDto` — агрегат
по (юзер × направление) без дневной разбивки → месячного предагрегата
достаточно для любой сборки. Если появится дневная детализация — партиция
хранит по-дневный агрегат (тот же принцип).

### Умная оптимизация №2: мгновенный частичный ответ

`POST /kpi-airtime/get` НЕ ждёт ничего:
- все месяцы в кэше → сразу готовый отчёт (текущее поведение сохранено);
- часть в кэше → `{ status: 'queued', progress: { totalMonths, readyMonths,
  months: [{ month: '2026-03', status: 'ready'|'queued'|'error' }] } }` +
  job-ы только на отсутствующие месяцы. Готовые партиции не пересчитываются.

### Защита Bitrix (требование «не перегрузить»)

- **Дедупликация**: jobId = ключ партиции → повторный клик / второй юзер
  с тем же периодом подписываются на тот же job, а не плодят прогоны.
- **Concurrency = 1 на домен** (Bull group/limiter): в один момент по
  порталу идёт ОДИН месячный сбор; месяцы — последовательно.
- **Приоритеты**: интерактивные запросы > cron-прогрев.
- **Дроп страницы рейт-лимитером = громкая ошибка job** (ретрай через
  Bull attempts/backoff), а не тихая дыра в данных (см. инцидент
  2026-07-27 в родительском доке).
- `maxRows` остаётся страховкой, но уже НА МЕСЯЦ (реально недостижим).

## 3. План работ

### Этап 1 — бэкенд: партиции + очередь (kpi-report-sales)

- [ ] 1.1 Ревизия текущего месячного кэша airtime: формат, ключи, TTL —
      привести к схеме `<report>:<vN>:<domain>:<YYYY-MM>` (версия в ключе).
- [ ] 1.2 Предагрегатор: raw-строки voximplant за месяц →
      `{ [userId]: { [direction]: { seconds, calls } }, rowsFetched, truncated }`.
- [ ] 1.3 Воркер месячной партиции (Bull): jobId = ключ партиции; тянет
      только свой месяц; пишет партицию в кэш (прошлые месяцы TTL 30д+,
      текущий — минуты); attempts/backoff; дроп лимитера → fail job.
- [ ] 1.4 Диспетчер в `POST /kpi-airtime/get`: период → список месяцев →
      кэш-чек каждого → готово всё: собрать и отдать отчёт; нет: поставить
      job-ы на недостающие, отдать `queued` + progress.
- [ ] 1.5 Сборщик отчёта из партиций: Σ по выбранным юзерам/месяцам,
      `truncated = OR` по партициям, `rowsFetched = Σ`.
- [ ] 1.6 WS-события в существующий сокет (паттерн sales-finance):
      `airtime:progress { requestKey, month, readyMonths, totalMonths }`,
      `airtime:done { requestKey }`, `airtime:error { requestKey, month }`.
- [ ] 1.7 Concurrency 1 на домен + приоритеты interactive/warmup.
- [ ] 1.8 OpenAPI: расширить response (`status`, `progress`) — НЕ ломая
      текущий формат готового отчёта.

## 4. Критерии приёмки

- Год × весь отдел: POST отвечает < 1 сек (queued), UI показывает
  «готово N из M месяцев», результат приезжает по WS; при отключённом
  WS — поллингом. Никаких network error.
- Повторный клик/второй пользователь с тем же периодом не создаёт второй
  прогон (лог воркера: один job на месяц).
- Смена состава сотрудников на уже прогретом периоде — мгновенно из кэша,
  без походов в Bitrix.
- В логах Bitrix-лимитера нет дропов при сборе года (месяцы идут
  последовательно, concurrency 1 на домен).
- Ошибка сбора месяца видна в UI («Повторить»), готовые месяцы не
  теряются; тихих неполных отчётов нет.
