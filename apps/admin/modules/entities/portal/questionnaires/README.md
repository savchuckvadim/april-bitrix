# Анкеты портала — раздел админки

Владелец портала собирает здесь анкеты: какие вопросы задать менеджеру при
планировании события и при отчёте по нему. Вопросы собираются **из полей,
которые пользователь завёл в Битриксе руками**.

Адрес: `/portal/[portalId]/questionnaires` (список) и
`/questionnaires/[questionnaireId]` (редактор, `new` — создание).

Контракт и правила — на бэке: `back/libs/portal-lib/store/questionnaires`
(README там) и `back/apps/admin/src/portal/questionnaires`. Полный план —
`front/docs/event-questionnaire-catalog.tasks.md`.

## Два экрана

**Матрица** — главный вид. Строки — типы событий (значения условий приходят
из `GET /schema`, в админке не зашит ни один код), колонки — назначение
анкеты: спросим при планировании или при отчёте. В ячейке — анкеты с числом
вопросов, состоянием и бэйджем сломанных привязок; в пустой ячейке кнопка
«Создать» с уже проставленными назначением и условием.

Анкеты **без условия по типу события** (только по стадии, по статусу работы
или «всегда») уходят в отдельный блок — иначе владелец решит, что их нет.
Анкета, покрывающая несколько типов, видна в каждой своей строке.

Плоский список остался вторым видом: код, версия, дата, массовые действия.

**Редактор** — одна страница: шапка (назначение двумя карточками, код
предлагается транслитом и дальше не меняется — это ключ уже собранных
ответов), конструктор условий, список вопросов, пикер полей, панель «в
Битриксе изменилось».

## Пикер полей

Носитель (компания, сделка, лид, контакт, смарт) → таблица живых UF-полей.
Метка **«Заведено вручную»** — поля, которых нет в нашей БД: ровно те, что
пользователь создал сам. Плюс «уже используется в анкете X».

Поле можно **завести прямо здесь** — оно создаётся в Битриксе и сразу
становится вопросом; существующее можно **синхронизировать**.

Пикер гасит с объяснением то, что бэк отклонит на сохранении: множественное
поле, тип вне матрицы, список без идентификаторов элементов (так бывает без
прав администратора CRM), смарт без потока события. Прятать такие поля
нельзя — владелец сам их завёл и искал бы пропажу.

## Живая правда Битрикса

Подписи и варианты лежат снимком в нашей БД (ради `bitrixId` — именно он
уходит в CRM). Чтобы снимок не расходился с правдой:

- редактор запускает сверку **сам при открытии**, тихо, без тоста;
- панель «В Битриксе изменилось» показывает переименования, появившиеся и
  исчезнувшие варианты, смену типа;
- применяется всё **по кнопке владельца**: подписи он пишет под менеджера, и
  затирать их автоматически нельзя. Без спроса система правит только адрес
  записи — `bitrixId` и гашение исчезнувшего варианта.

Чтобы «переименовано в Битриксе» не загоралось на каждой анкете, в `meta`
вопроса хранится **принятый** слепок подписи: сравнивается живое с ним, а не
с формулировкой вопроса.

## Правила слайса

- `@workspace/nest-admin-api` импортируется только в `lib/api/*-helper.ts`;
- ни одного кода (назначение, контрол, канал, вид условия, значение условия)
  в админке не хардкодится — всё из `GET /schema`;
- редактор повторяет правила бэка **до** отправки, теми же формулировками:
  собрать заведомо отвергаемое нельзя;
- удаления вопроса в интерфейсе нет — только гашение;
- логика раскладки и представления — чистые функции в `lib/*-view.ts` с
  тестами, компоненты только рисуют.
