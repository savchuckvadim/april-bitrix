## 2. Почему новый реквизит не создаётся

Разобрано по коду, порядок — по весу. Пункт 2.3 требует проверки на живой БД (докер был
выключен).

1. **Карточка исчезает без типа клиента.** `BxRqBaseEdit` делает `if (!clientType) return null`.
   У сделки без `op_client_type` блок «Основная информация» не рендерится вовсе — ни «Добавить
   реквизиты», ни «Редактировать». При этом `BxRqPage` жёстко считает тип `ORGANIZATION`, а
   листенер подставляет `ORGANIZATION` как фолбэк: три ответа на один вопрос.
2. **Модалка не открывается на пустом шаблоне.** `BxRqBaseEdit` показывает `BxRqEditModal` только при
   `creating.fields.length > 0`. Черновик нового реквизита — копия `current.item`, а он для типа без
   реквизитов равен `rqData.default`. Если бэк не отдал `default`, адаптер `fromGroupDto` подставляет
   `EMPTY_RECORD` с `fields: []` — кнопка «Добавить реквизиты» нажимается, и ничего не происходит.
3. **Заготовки `-1` на бэке привязаны к пресетам 1/3/5.** `requisite.service.getRq` дописывает
   недостающие типы как `BXRequisiteDTO({ID: -1, PRESET_ID: 1|3|5})` (хардкод), а маппер группирует
   строгим `===` по `bitrix_id` портала из `bx_rqs` (строка) против `PRESET_ID` (число из заготовки
   или строка из REST). Если пресеты портала установлены через pbx-install и их id не 1/3/5,
   заготовки не попадают ни в `org`, ни в `ip`, ни в `fiz` → `default: null` → пункт 2. Ремап
   1/3/5 → пресет портала есть только в ветке «у компании нет ни одного реквизита», и там ради
   шаблона создаётся и тут же удаляется реквизит в Битриксе на каждый `get_rq`.
4. **Создание берёт не ту заготовку.** `updateRequisite(-1)` ищет `bxRqs.find(ID === -1)` — первую
   заготовку (орг), даже когда создаём ИП или физлицо; тип спасает только `preset_id` из запроса
   (`PRESET_ID = erqItem.preset_id || ORG`). Адреса и банк заготовки в `crm.requisite.add` не уходят:
   их надо сохранять следующими вызовами (вкладки появляются после сохранения базы — это ок).
5. **Второй реквизит того же типа невозможен по модели.** `setCurrentRqItems` отдаёт заготовку
   только когда `items` пуст. В Альфацентре так же: там «новый» — это заполнить единственную
   пустую заготовку.
6. **Тип клиента без обратной связи.** Нет селектора (в легаси был на экране договора), нет записи
   в сделку/компанию, нет фолбэка на компанию; листенер не реагирует на смену типа и на
   `saveBaseCreating`. Альфацентр при пустом типе берёт тип единственного заполненного реквизита и
   пишет его в сделку.
7. **Текущий реквизит сделки не запоминается** (заглушки в `current-rq.util.ts`); после перезагрузки
   выбирается первый.
8. **Сделка без компании** — `fetchBXRQ` не вызывается, страница молча показывает «Реквизиты не
   загружены».
9. **Типизация id пресетов.** `PRESET_ID?: number` в `BXRequisiteDTO`, а REST отдаёт строки;
   `bitrix_id` в Prisma — `String?`. Сравнения `===` в пяти местах (service ×2, mapper ×3).

## 3. «Рыба» договора: что мешает

- Фронт: `generateContract` возвращает `false`, если `contractValidationErrors` (обязательные поля
  сделки + `missingRequisites`) не пуст. Кнопка не задизейблена, но нажатие даёт «Не заполнено: …».
- Бэк уже умеет прочерки для номера договора, дат, даты предоплаты, названия/ИНН клиента, документа
  физлица и шапки (директор/должность/основание). Чего не хватает:
  - `client_direct_position` / `client_direct_fio` → пустая строка вместо прочерка;
  - адрес: `getAddressString` клеит `field.value + ', '` и для пустых полей → «undefined, , ,»;
  - для орг/ИП `client_rq` — только название и ИНН; легаси PHP печатал название, адрес, телефон,
    ИНН, банк, р/с, к/с, БИК, прочее — каждую строку с прочерком, если пусто;
  - баг `docDate = \`Документ выдан: ${docDate || docDate}\`` — дата выдачи всегда прочерк.
- Отчёт о поставке использует те же проверки (`supplyReportValidationErrors`). Владелец сказал
  «именно для договора» — отчёт остаётся строгим (см. вопрос 3).

## 4. Решения владельца

1. **Куда писать тип клиента** при смене в приложении: в сделку (сейчас читаем её), в компанию
   (как легаси) или в обе. Предлагаю: читать сделка → компания → «Коммерческие»; писать в обе.
2. **Текущий реквизит сделки:** хранить в слепке (v2, поле `rqId`) без нового поля Битрикса.
   В Альфацентре было поле сделки; в конструкторе реквизит уходит в payload документов целиком,
   поле не нужно. Подтвердить.
3. **Рыба:** только договор; отчёт о поставке строгий. Нужно ли подтверждение перед генерацией
   рыбы, или достаточно жёлтого предупреждения и надписи на кнопке «Сформировать рыбу договора»?
4. **Состав `client_rq` для орг/ИП** — как в легаси PHP (название, адрес, телефон, ИНН, банк,
   р/с, к/с, БИК, прочее). КПП/ОГРН легаси в этот блок не печатал. Оставить легаси-набор?
5. **Несколько реквизитов одного типа** — закладываю кнопку «Новый реквизит» всегда (пункт 2.5),
   не только при пустом типе. Подтвердить.

## 7. Маркетплейс: модуль реквизитов отдельным приложением

Цель: приложение Bitrix24 «Реквизиты клиента» — вкладка в карточке компании и сделки, установка
пресетов и полей, заполнение с подсказками и склонениями, витрина на маркетплейсе. Делать после
раздела 5; но шаг 1 ниже выгодно сделать прямо в ходе раздела 5, чтобы код не переписывать дважды.

### Что переносится

| Часть | Откуда | Что обобщить |
| --- | --- | --- |
| Домен (чистый TS) | коды полей и `includes` по типам (`CodesField`), типы `RqRecord/RqItem/Address/Bank`, фильтры, проценты заполнения, имя для списка, падежи (`rq-case`, lvovich/russian-nouns-js), валидации обязательных | Вынести в пакет `rq-domain` без зависимостей от Nest/Redux; им пользуются и конструктор, и новое приложение |
| Бэк | `rq-lib` (get/store/update_address/case), `pbx-install/modules/rq` (установка и синк пресетов/полей, мониторинг) | Зависимости спрятать за интерфейсы: `PortalGateway` (REST-клиент по домену), `PresetRepository` (пресеты портала), вместо `PBXService.init`/`PortalModel`; `@/modules/bitrix` заменить на тонкий клиент |
| Фронт | `entities/bx-rq` (слайс, thunks, UI базы/адресов/банка/модалки) | UI не тянуть из `@workspace/ui`/`april-ui` монорепы: у приложения свой набор (shadcn-копия или `@bitrix24/b24ui`); данные — через `b24jssdk` (`B24Frame`) и свой бэк |

### Чего в конструкторе нет, а приложению нужно

- Установка через OAuth: `ONAPPINSTALL`, хранение и обновление токенов по порталу, своя БД
  (порталы, пресеты, поля, настройки, журнал установки).
- Placement: `CRM_COMPANY_DETAIL_TAB`, `CRM_DEAL_DETAIL_TAB`; скоупы `crm`, `placement`,
  `user_brief`.
- Настройки портала: откуда брать тип клиента (своё перечисление или выбранное UF-поле
  сделки/компании), какие пресеты ставить, обязательные поля для документов.
- Биллинг — подписка маркетплейса, своего не нужно. Публичный HTTPS-домен, страница поддержки,
