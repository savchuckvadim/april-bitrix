# Чек-листы и вопросы события

Механизм «получить от менеджера то, что знает только он»: показать поля
CRM (с текущими значениями) в нужный момент работы и записать ответы.

## Что где лежит

| Файл | Роль |
|---|---|
| `data/checklist-catalog.ts` | **единственный источник состава**. Внутри два блока: `PLAN_CHECKLIST_CATALOG` (что нужно знать ДО следующего звонка) и `REPORT_QUESTION_CATALOG` (что выяснили В разговоре). Наружу экспортируется общий `CHECKLIST_CATALOG` — их объединение |
| `type/call-checklist.type.ts` | форма записи каталога |
| `lib/checklist-selectors.ts` | активность набора, «поле не заполнено», срок годности значения |
| `lib/checklist-values.ts` | резолв поля по слепку портала, чтение текущего значения |
| `model/CallChecklistThunk.ts` | запись в CRM (дебаунс, явная очистка) |
| `ui/ChecklistInlineCard.tsx` | блок в колонке (`place`), `ui/CallChecklistDialog.tsx` — модалка перед отправкой |

Разделение на два блока — только для читаемости файла: движок работает с
общим каталогом, `PLAN_CHECKLIST_CATALOG` наружу не экспортируется.

## Как добавить набор вопросов

Одна запись в каталоге + одна настройка портала. Кода писать не нужно.

```ts
{
    id: 'reportRefine',              // уникальный id, добавить в ChecklistId
    title: 'Итог доработки',
    hint: 'Что мешает клиенту купить прямо сейчас.',
    trigger: { kind: 'reportType', eventType: 'refine' },
    configKey: 'withReportQuestions', // флаг из DomainFeatureConfig
    presentation: 'inline',           // 'inline' | 'modal'
    place: 'report',                  // 'plan' (по умолчанию) | 'report'
    fields: [ /* см. ниже */ ],
}
```

**Когда показывать (`trigger`)**

| Вид | Условие |
|---|---|
| `planType` | менеджер планирует звонок этого типа |
| `reportType` | менеджер отчитывается по звонку этого типа |
| `targetStage` | отправка двинет основную сделку на эту стадию (через предикт) |

**Где показывать**: `presentation: 'inline'` + `place` — блок в колонке
плана или отчёта; `presentation: 'modal'` — шаг-модалка в цепочке
отправки (модалки идут одна за другой, подтверждённые пропускаются).

**Поле набора**

```ts
{
    code: 'op_objection_reason', // код pbx-поля из реестра
    type: 'enumeration',         // date | datetime | enumeration | money | string
    title: 'Возражение клиента',
    placeholder: 'Как клиент сказал своими словами', // только для string
    required: false,             // true блокирует отправку, пока пусто
    staleAfterDays: 30,          // ТОЛЬКО для дат: старое значение снова требует ответа
    channel: 'crm',              // 'crm' (по умолчанию) | 'dto' (пишет бэк при отправке)
    native: true,                // штатное поле Bitrix (OPPORTUNITY), слепок не нужен
}
```

Носитель поля выбирается сам: компания → сделка → лид, первая сущность,
где поле установлено на портале и строка загружена. Поле не установлено —
контрол не рисуется и отправку не блокирует (самогейт).

## Как включить набор на портале

1. Завести флаг в `modules/app/consts/domain-config.ts` (`DomainFeatureConfig` + дефолт `false`).
2. Завести настройку с ТЕМ ЖЕ именем ключа в бэковой схеме:
   `back/libs/portal-lib/store/app-settings/portal-app-settings.schema.ts`,
   секция `eventSales`. Фронт берёт только те ключи, что совпали по имени и типу.
3. Включить в админке: Портал → Settings → event-sales.

## Чего пока НЕТ

**Состав каталога не настраивается с портала.** Сейчас это данные в коде:
добавить вопрос или поправить формулировку можно только релизом, и на
всех порталах состав одинаков — настройками регулируется лишь
включение набора целиком.

Разбор и план перехода на портальный каталог (вопросы приходят с бэка,
редактор в админке) — `front/docs/event-questionnaire-analysis.md`,
этап 3. Там же обоснование, почему адрес записи ответа должен оставаться
частью описания вопроса: указан код поля — ответ ложится структурно и
попадает в отчёты, не указан — уходит текстом.
