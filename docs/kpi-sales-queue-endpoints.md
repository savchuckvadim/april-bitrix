# Задача: сборочные эндпоинты kpi-report-sales — очередь (WS + поллинг) + сквозное кэширование

Дата постановки: 2026-07-27. Приоритет: высокий (прод-инцидент).
Две части одной цели «запросы не висят минутами»: (1) очередь вместо
синхронных ручек, (2) кэш прошедших периодов + прогрев.

## Инцидент

Прод, портал во фрейме: `POST /api/kpi-airtime/get` за большой период —
запрос «висит» бесконечно, повторный — `500 Internal Server Error`.

**Причина.** Ручка синхронная: пагинация `voximplant.statistic.get`
(`fetchRows`, while по `response.next`) крутится ПРЯМО в HTTP-запросе под
рейт-лимитером Bitrix (~2 стр/сек). Большой период × отдел = сотни страниц
→ десятки минут при открытом соединении:

- «висит» — соединение живёт, пока бэк тянет страницы;
- `500` — обрыв на длинной дистанции (таймаут прокси/номер страницы/OOM —
  уточнить по серверным логам);
- повторный клик фронта запускает ПАРАЛЛЕЛЬНЫЙ такой же расчёт (дубль
  нагрузки на лимитер, каскадное замедление);
- месячный кэш airtime не спасает: первый прогон должен дожить до конца,
  а он синхронный.

## Подтверждение по прод-логам (2026-07-27, ~16:27–16:32)

- Дубли расчётов: «voximplant.statistic.get: собрано 1230/278/3456/2808
  строк» повторяются по 2–3 раза с одинаковыми числами — один и тот же
  сбор идёт параллельно (повторные клики/ретраи, дедупликации нет).
- `[gsirk.bitrix24.ru] превышен лимит попыток rate limiter, пропускаем`
  (WARN, многократно) — вызовы к Bitrix ДРОПАЮТСЯ под перегрузом:
  (а) вероятный источник 500 (дроп → пустой результат → падение выше);
  (б) риск ТИХО НЕПОЛНОГО отчёта — часть страниц пропущена без ошибки.
  Отдельно проверить обработку дропа: пропуск обязан быть громкой
  ошибкой расчёта, а не молчаливой дыркой в данных.
- «Cannot GET /api/kpi-report/get» из логов — ручное открытие URL в
  браузере (GET, внутренний IP, без referer), к инциденту не относится.

## Целевая архитектура (образец уже в проде — sales-finance)

`sales-finance/closed-sales|hot-clients` уже работают правильно:

1. POST ставит job в Bull (`QueueDispatcherService`, jobId — дедупликация
   по ключу запроса) и мгновенно отвечает `{ status: 'queued' }`.
2. Воркер считает, кладёт результат в кэш (v-ключ по фильтрам).
3. Доставка: WS-событие `*:done` (socketId/комната домена) + фолбэк —
   тот же POST возвращает готовый результат из кэша (поллинг).

## Обязательные свойства решения

- **Дедупликация**: jobId из ключа запроса (домен+фильтры) — повторный
  клик НЕ порождает второй расчёт, а подписывается на тот же результат
  (как buildFinanceRequestKey / `share-refresh-<token>`).
- **Поллинг-фолбэк обязателен**: WS может не подняться (прокси без
  upgrade) — фронт перезапрашивает тот же POST раз в N секунд, пока
  `{status:'queued'}` не сменится результатом (паттерн finance-слайса).
- **Прогресс**: воркер airtime может публиковать прогресс по месяцам
  (опционально, WS-событие progress) — UI показывает «собрано N из M мес».
- **Таймаут/ретрай job**: Bull attempts/backoff; упавший job → WS-событие
  error + статус error в кэше (фронт показывает «Пересчитать»).
- **Лимит параллелизма** воркера на домен — не давить рейт-лимитер Bitrix
  (очередь уже сериализует; проверить concurrency).

## Фронт (kpi-sales)

- airtime/report/callings-слайсы: статус `queued` + подписка на WS-событие
  + поллинг-фолбэк — скопировать механику `finance-ws.listener` /
  `closedSalesArrived` (матчинг по requestKey, отсев устаревших ответов).
- Кнопка «Пересчитать» (forceRefresh) — как в финансах.
- Прелоадеры уже есть; добавить «долгий» текст для первого прогрева.

## Часть 2. Сквозное кэширование отчётных данных

Симптом того же семейства: `net::ERR_EMPTY_RESPONSE` на
`/kpi-airtime/get` — сервер/прокси оборвал соединение, не ответив
(перегруженный синхронный расчёт умер по дороге). Очередь убирает обрыв,
кэш убирает саму долгую работу.

### Принцип: прошлое неизменно — кэшируем агрессивно

- **Прошедшие дни/недели/месяцы/кварталы/годы** — кэшировать
  ОБЯЗАТЕЛЬНО, по каждому виду отчёта/подотчёта:
  - `kpi-report/get` (события),
  - `kpi-report/calling-statistic` (звонки),
  - `kpi-airtime/get` (эфирное время — месячный кэш уже есть, добить),
  - `sales-user-report` (user report — приходящие данные тоже из этих
    источников, должен собираться из тех же кэш-партиций),
  - sales-finance — уже партиционирован по месяцам (эталон).
- **Партиционирование по месяцам** (паттерн closed-sales/airtime):
  произвольный период = Σ готовых месячных партиций + живой хвост
  текущего месяца. Прошлые месяцы — длинный TTL (30д+), пересчёт только
  по forceRefresh.
- **Ключи** — единая схема `<report>:<vN>:<domain>:<partition>:<фильтры>`
  (как sales-finance): версия в ключе = дешёвая инвалидация формата.

### Текущий день (intraday) — вторым приоритетом, можно позже

- Идея stale-while-revalidate: отдать кэш сразу, под капотом дёрнуть
  пересчёт, если результат отличается — допушить по WS. Помечено как
  «сложное, может и не нужно» — НЕ блокирует часть 1 и кэш прошлых
  периодов. Достаточно короткого TTL (минуты) на сегодняшний хвост.

### Прогрев и восстановление кэша

- **Cron-прогрев**: ночью по активным порталам прогревать партиции
  прошедших месяцев для каждого вида отчёта (структура отдела уже
  известна). Утром даже годовые отчёты открываются из кэша.
- **Ручка восстановления** `POST <report>/cache/warmup {domain, period?}`
  (или общая): если кэш пришлось убить (Redis flush, смена версии
  ключей) — одним вызовом переналить партиции, не дожидаясь, пока
  пользователи по одному прогреют их своими висящими запросами.
  Прогрев идёт через ту же очередь (не бомбит rate limiter).
- Прогрев/восстановление обязаны уважать лимитер: последовательные
  job-ы с низким приоритетом, а не парallel-бомбёжка.

### Порядок работ

1. Часть 1 (очередь + дедуп + WS/поллинг) — снимает висящие соединения.
2. Партиции прошлых периодов для kpi-report/calling-statistic
   (airtime — добить, finance — готов), user-report поверх партиций.
3. Cron-прогрев + ручка warmup.
4. Intraday stale-while-revalidate — опционально, последним.

## Часть 3. Публичные ссылки (share): создание и копирование во фрейме

Наблюдения в проде 2026-07-27 (фрейм Bitrix):

1. **Создание ссылки крутилось бесконечно** (возможно, было обновление
   страницы во время создания):
   - у create нет таймаута/ретрая — если POST завис (бэк в этот момент
     был задушен синхронным airtime — см. часть 1), спиннер вечный;
   - после reload страницы диалог теряет состояние create: если ссылка
     реально создалась (PENDING), UI об этом не знает.
   - Сделать: таймаут на create + понятная ошибка с «Повторить»;
     после reload — список ссылок сам показывает свежую PENDING-ссылку
     (поллинг статуса до ACTIVE, бейдж «готовится»); дедуп по клиентскому
     токену уже есть (повторный create с тем же токеном → 409 → показать
     существующую, а не вечный спиннер).

2. **Копирование в буфер во фрейме так и не работает** (фикс
   copyTextToClipboard/execCommand задеплоен? проверить сначала именно
   это — сборка Vercel могла быть старой). Если и execCommand не
   пробивается — НЕ полагаться на буфер вообще:
   - в success-панели диалога и в списке ссылок показывать URL
     **кликабельной ссылкой** (`<a target="_blank" rel="noopener">`) —
     «открыть в новой вкладке» работает во фрейме всегда, оттуда адрес
     копируется из адресной строки;
   - рядом — выделяемый текст URL (input readonly с автовыделением по
     клику) для ручного Ctrl+C;
   - кнопку «Скопировать» оставить как best-effort, но с честным
     фидбеком: «не удалось — скопируйте вручную/откройте ссылку».
