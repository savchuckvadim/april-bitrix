## 0. Что УЖЕ сделано (2026-07-30, в проде) — контекст

- Обе ручки (`POST /kpi-report/get`, `POST /kpi-report/calling-statistic`)
  переведены на очередь: `mode=queue` → мгновенный конверт
  `{status: ready|queued|error, data?, requestKey, message?}`; compute в
  `SalesKpiReportQueueProcessor`; jobId-дедуп по нормализованному ключу
  `{domain}:{fromIso}_{toIsoInclusive}:{sortedUserIds}`; строгий батч
  (упавший чанк/пропавшая команда = громкая ошибка, а не тихо неполные
  счётчики); WS `kpi-report:done|error`,
  `kpi-report:calling-statistic:done|error` (done несёт данные);
  поллинг-фолбэк 7с на фронте; отсев устаревших ответов по requestKey.
- Кэш — конверт РЕЗУЛЬТАТА целого периода:
  `app-cache:{kpi-report|calling-stat}:{domain}:0:v1:result:{from}_{to}:{ids}`;
  TTL: период задевает сегодня — 180с, полностью прошлый — 30 дней,
  error-конверт — 120с.
- Ограничение текущей модели (мотивация этого дока): ключ включает ВЕСЬ
  период и состав. «Год» кэшируется только как «этот год + эти люди»;
  месяц из прогретого года = другой ключ = полный пересчёт; «два года» ≠
  «год из кэша + год новый». У airtime эта задача уже решена месячными
  партициями — здесь нужен тот же паттерн.

## 1. Цель

1. Произвольный период = Σ готовых месячных партиций счётчиков + живой
   хвост текущего месяца (модель airtime).
2. Смена периода/состава на прогретых месяцах — из кэша, без Битрикса.
3. Стрим-UX: данные появляются в таблице по мере готовности месяцев
   (паттерн user-report/airtime), компактный индикатор вместо блокировки.

## 2. Почему счётчики партиционируются (проверено)

- calling-statistic: 6 бакетов — счётчики звонков за период
  (`result_total` по фильтру `>CALL_START_DATE/<CALL_START_DATE`).
  Счётчик аддитивен по непересекающимся месяцам: count(период) =
  Σ count(месяц). Партиция месяца = 6 чисел × N сотрудников.
- kpi-report/get: счётчики `lists.element.get` по `sales_kpi_event_date`
  в границах месяца — аддитивны так же. Партиция месяца = count по
  каждому (сотрудник × действие).
- ВНИМАНИЕ, отличие от airtime: партиция ЗАВИСИТ от состава действий
  портала (kpi) — версия партиции должна включать хэш конфигурации
  действий (см. 3.2), иначе смена настроек портала отдаст старые составы.

## 3. План — бэкенд (`src/report`)

      существующими `v1:result:*` (схема заложена):
      `v1:month:{yyyy-MM}:{usersKey}` — calling;
      `v1:month:{yyyy-MM}:{usersKey}:{actionsHash}` — kpi (см. 3.2).
      ВАЖНО: в отличие от airtime составы НЕ портал-wide (см. 3.3) —
      usersKey остаётся в ключе партиции.

### 3.2 Хэш конфигурации действий (только kpi-report)

- [ ] `buildActionsConfigHash(currentActionsData)` — стабильный короткий
      хэш (sha1→8 симв.) отсортированных `action.code+bitrixId` — в ключ
      партиции kpi. Настройки портала поменялись → новые ключи, старые
      умирают по TTL.

### 3.3 Решение по составу сотрудников (принять при старте)

Вариант А (проще, рекомендую первым): партиция на КОНКРЕТНЫЙ состав
(usersKey в ключе). Плюс: механика 1-в-1 с result-кэшем; минус: смена
состава = свой прогрев (но месяцы независимы — прогрев инкрементальный).
Вариант Б (портал-wide, как airtime): счётчики ПО КАЖДОМУ сотруднику
отдельно в партиции месяца, сборка суммирует запрошенных. Для calling
это ×N команд на месяц как сейчас (терпимо); для kpi — сотрудник×действие
уже и так по-отдельности → Б почти бесплатен и лучше; НО прогрев месяца
тянет весь портал. Стартовать с Б для kpi/calling обоих, если объём
команд на месяц ≤ ~300; иначе А. Зафиксировать решение здесь.

## 5. Cron-прогрев (B4, общий для airtime + counts)

Решение 2026-07-30 (обсуждено): НЕ «пересобирать всё за 3 года каждые
выходные» — прошлые месяцы неизменяемы, еженедельный пересбор = часы
пустой долбёжки лимитера. Память не ограничение (ячейка ~150 Б;
100 сотрудников × 36 мес ≈ 0.5 МБ/портал).

- [ ] Ночь на 1-е число: прогрев СВЕЖЕЗАКРЫВШЕГОСЯ месяца по активным
      порталам (airtime + партиции counts, когда появятся).
- [ ] Еженедельно ночью (сб/вс): «сверка дырок» — маркеры за скользящие
      36 мес, job'ы ТОЛЬКО на отсутствующие месяцы. Идемпотентно: всё
      собрано → ноль запросов в Битрикс (только чтение кэша).
- [ ] Низкий приоритет Bull (интерактивные запросы всегда важнее;
      у airtime уже зарезервирован AIRTIME_PRIORITY_WARMUP=10),
      последовательные job'ы, никакой параллельной бомбёжки.
- [ ] Ручка `POST <report>/cache/warmup {domain, period?}` — переналить
      партиции после reset/смены версии ключей через ту же очередь.
- [ ] Ретро-правки данных в CRM: ручной cache/reset + «Пересчитать»,
      не автоматика.

## 6. Критерии приёмки

- Год × отдел: POST < 1с; таблицы наполняются по мере готовности месяцев;
  прогресс и ETA видны компактным бейджем; WS off → доезжает поллингом.
- Месяц из прогретого года — мгновенно из кэша (ключевой сценарий).
- Два года после прогретого года — прогресс стартует с 12/24, в Битрикс
  уходят только недостающие месяцы.
- Смена настроек действий портала (kpi) не отдаёт старые составы
  (actionsHash в ключе).
- Дроп команды лимитером = ошибка месяца с «Повторить», не тихая дыра.
- В логах нет дублей прогонов (дедуп jobId) и «Skipping failed batch».
